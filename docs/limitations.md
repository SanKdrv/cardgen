# Ограничения и план развития

## Ограничения текущего прототипа

### Проверка фактов

- **Эвристики, а не понимание смысла.** Guard сверяет числа, единицы, коды и
  дословные значения, но не проверяет логическую связность утверждений.
  Фраза «подходит для пищевой промышленности» будет поймана, а «подходит
  для ответственных узлов» — нет.
- **Числа словами не проверяются.** «Два выхода», «пять лет» не попадут
  в проверку. На практике модель почти всегда пишет цифрами, но это дыра.
- **Единицы не конвертируются.** `1,6 МПа` нельзя заменить на `1,6 бар` или
  `16 бар`, даже если это физически одно и то же: guard считает смену
  единицы искажением факта.
- **Структурированные характеристики берутся только из `specs`.** Если
  класс точности упомянут лишь в свободном описании паспорта, он попадёт
  в текст, но не в `key_specs` и может остаться в списке «уточнить».
  Автоматически извлекать таблицы из паспорта прототип не умеет.
- **Список маркеров свойств всё ещё неполный.** Он покрывает основные
  материалы, интерфейсы, защиту, сертификаты, страны, цены и сервисные
  обещания, но не все возможные домыслы.
- **Единицы распознаются по словарю и латинскому шаблону.** `psi`, `атм`,
  `Па`, `°F`, «1,6 бара», «1,6 атмосферы» и другие частые формы отклоняются.
  Дословное `24VDC`/`220VAC` из входа не считается выдумкой. Экзотическая
  кириллическая единица вне словаря может остаться незамеченной.
- **Упоминание отсутствующей характеристики запрещено.** Если поля нет в
  `specs` и в описании, фраза «класс точности — 1,5» отклоняется; допустимы
  только «данных нет», «не указан», «уточните». Если факт есть в свободном
  описании паспорта, упоминание разрешено, но в `key_specs` он не попадёт.
- **Отрицание учитывается в пределах предложения.** «Не предназначен для
  агрессивных сред», «поверка не требуется», «поверка отсутствует» и
  «запрещена» распознаются. Сложные конструкции с модальностью
  («допускается», «может применяться») остаются эвристикой.
- **Римские цифры и числа словами не проверяются.** «Класс точности III» и
  «два выхода» не попадут в числовую проверку — это следующий шаг.
- **Ложные срабатывания возможны.** Число, совпавшее с годом или артикулом,
  может быть принято за факт; редкие технические обозначения — отклонены.

### Контент и SEO

- **Качество текста не измеряется автоматически.** Длины и факты
  проверяются, но убедительность и естественность формулировок — нет.
- **Нет A/B-тестов и анализа выдачи.** Поисковые запросы формируются
  эвристически, без частотности и конкуренции.
- **Один язык.** Промпты и интерфейс рассчитаны на русский; для других
  языков нужны отдельные правила и проверки.
- **Нет склонений и морфологии.** Запросы и тексты могут звучать
  канцелярски; редактору всё равно нужно вычитать результат.

### Входные данные

- **Только JSON и форма.** PDF-паспорт, скан или Excel не парсятся.
- **Нет OCR и извлечения таблиц.** Это следующий очевидный шаг для
  реального каталога.
- **Описание считается источником фактов целиком.** Если в паспорте есть
  маркетинговое преувеличение, оно может попасть в карточку.
- **Нет дедупликации товаров.** Один и тот же прибор под разными названиями
  будет обработан дважды.

### Инфраструктура

- **Stateless, без БД.** История, версии и совместная работа не поддерживаются.
- **Пакетная обработка последовательная.** 20 товаров = 20 запросов подряд;
  для больших выгрузок нужна очередь.
- **Нет кэширования.** Повторный запрос с теми же данными снова обращается
  к LLM.
- **Нет авторизации и rate limiting.** API рассчитан на локальный запуск
  или доверенную сеть.
- **Нет учёта стоимости.** В мете есть только задержка и число попыток.
- **Нет трассировки.** Логи структурированы минимально; для продакшена
  нужны OpenTelemetry и сбор метрик.
- **Промпт-инъекция снижена, но не исключена.** Текст паспорта изолирован
  в блоке данных, однако модель всё ещё может последовать скрытой
  инструкции. Guard поймает новые числа и коды, но не все формулировки.

### Провайдеры

- **Нет строгой JSON Schema.** Используется `response_format=json_object`;
  провайдеры со `json_schema` могут дать более стабильный ответ.
- **Нет автоматического выбора модели.** Модель задаётся конфигом.
- **Нет стриминга.** Для веб-формы это не критично, для чата — важно.

## План развития

### Ближайшее (1–2 дня)

1. **Набор оценочных кейсов.** 20–30 товаров с эталонными фактами и
   регрессионный прогон: доля fallback, число нарушений, время.
2. **Строгая JSON Schema для провайдеров, которые её поддерживают.**
3. **Кэш ответов** по хэшу входа и версии промпта (файловый или Redis).
4. **Загрузка PDF** с извлечением текста и таблиц (`pymupdf` + LLM для
   структурирования), с обязательным подтверждением человеком.
5. **Словарь синонимов и единиц** для нормализации `бар`/`МПа`, `°C`/`C`,
   резьб и присоединений.

### Среднее (1–2 недели)

1. **PostgreSQL + история карточек.** Версии, статусы «черновик / на ревью /
   опубликовано», автор изменений.
2. **Очередь задач** (Celery/RQ/ARQ) для пакетной обработки и ретраев.
3. **Авторизация и лимиты** на API.
4. **Метрики и трассировка:** Prometheus, OpenTelemetry, стоимость токенов.
5. **Проверка SEO-качества:** частотность запросов, длина title, наличие
   ключей, сравнение с конкурентами.

### Дальше

1. **Интеграция с 1С-Битрикс:** выгрузка черновика в инфоблок, обратная
   синхронизация статусов.
2. **RAG по каталогу и регламентам:** единый глоссарий, согласованные
   формулировки, проверка на дубли.
3. **Мультиязычность** и отдельные промпты под площадки.
4. **Человеко-машинный цикл:** интерфейс правок с фиксацией, какие
   формулировки редактор изменил, и дообучение промпта на этих правках.
5. **Локальный контур:** vLLM + Qwen/DeepSeek, замер качества на своих
   данных, сравнение с внешними API по стоимости и задержке.

## Что осознанно не делалось

- CMS, админ-панель, деплой — по условиям задания не требуются.
- Векторная база — для одной карточки не нужна.
- Микросервисы — прототип должен запускаться одной командой.
- Полноценный парсер PDF — важнее было закрыть основной сценарий и
  показать, где проходит граница автоматизации.
